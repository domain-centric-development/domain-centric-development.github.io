Domain-Centric Development

The domain at the center.
Everything else points inward.

Domain-Centric Architecture is a practical synthesis of Domain-Driven Design, Hexagonal Architecture and Clean Architecture — documented as a compact guide, packaged as building blocks and executable rules for Java and .NET, proven in the same webshop built twice, and published as machine-readable knowledge your AI tooling can build from.

the mark is the architecture: one bounded context — adapters on the boundary, the domain at the core, neighbor contexts each with a core of their own

Infrastructure → Adapters → Application → Domain

One rule governs everything: dependencies point inward. The domain layer knows no framework, no database, no protocol — and an ArchUnit test suite fails the build when anyone forgets.

Why it is built this way

Architecture an agent can be held to

DCA is meant for building software with AI. Not because the patterns are new — because a model that writes fast needs a boundary it cannot argue with. Every part of this project exists to give it one.

  1. 01

    The rules are executable, and they have ids

    More than a hundred rules, each with an id like DCA-USE-009, shipped as a library for Java and .NET. An agent's output is judged by a build, not by review taste — and the same id means the same rule in both stacks.

  2. 02

    The doctrine is machine-readable

    Guide text, marker contracts and every rule as one cross-linked graph in Open Knowledge Format. The agent builds from the catalog instead of from a half-remembered blog post — and cites the node it used.

  3. 03

    The tooling puts it to work

    Skills, review agents and scaffolding that bootstrap a project, review a change against the rules and answer questions from the catalog. Tool-agnostic doctrine, with a Claude Code implementation you can install today.

  4. 04

    The proof is two webshops

    The same shop in Java and .NET, drafted mainly by Claude, directed and reviewed by the author — and green against the same rule catalog and the same end-to-end suite.

Principles

Opinionated where it pays, pragmatic where it doesn't

  • Framework-free domain Business logic depends on nothing. Spring lives in adapters and infrastructure.
  • Ports & adapters Use cases behind typed input ports; repositories, stores and publishers behind output ports.
  • Architecture as tests Structural rules are executable tests — ArchUnit in Java, ArchUnitNET in .NET, same rule ids. What needs judgement is marked as review, not quietly assumed. Erosion fails the build, not the retrospective.
  • Ubiquitous language Names come from the domain, per bounded context. No Manager, Helper or Util.
  • Progressive complexity Start with the four layers and no nesting inside them. Sub-packages arrive when the code asks for them.
  • Pattern choice per subdomain Core subdomains get the full tactical toolbox; supporting ones may stay simple.
