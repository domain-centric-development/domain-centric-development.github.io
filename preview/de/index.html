Domain-Centric Development

Die Domäne im Zentrum.
Alles andere zeigt nach innen.

Fachregeln landen in Controllern, Datenbank-Entities und Service-Klassen – verstreut, teils doppelt, ohne eine Quelle der Wahrheit. Ein Agent, der schnell schreibt, ist in Wochen dort. Wir legen die Fachlogik in die Domäne und lassen den Build das erzwingen, in Java und .NET.

Was ihr davon habt was zusammengehört, liegt an einer Stelle und wird zusammen geändert, ein Framework-Update fasst die Fachlogik nicht an, der Build nennt die verletzte Grenze beim Namen, und ein Agent wird an denselben Erwartungen gemessen wie ein Kollege.

Architekturtest einbauen Guide lesen Beispiel ansehen

die Marke ist die Architektur: ein Bounded Context – Adapter auf der Grenze, die Domäne im Kern, ein Aufruf kommt herein, seine Antworten gehen hinaus; Nachbarkontexte mit je einem eigenen Kern

Infrastructure → Adapter → Application → Domain

Eine Regel steht über allem: Abhängigkeiten zeigen nach innen. Die Domäne kennt kein Framework, keine Datenbank, kein Protokoll – und eine ArchUnit-Suite bricht den Build, wenn das jemand vergisst. Sie prüft die Struktur; ob das Modell richtig ist, bleibt eine Frage an Menschen.

1 · der Fehler 
package shop.checkout.domain;

import shop.checkout
  .infrastructure.persistence
  .OrderRow;

Eine Entity greift nach der Tabellenzeile, in der sie zufällig gespeichert wird. Nichts hält sie davon ab, und ein Jahr später lässt sich das Modell nicht mehr ohne die Datenbank ändern.

2 · die Regel, die das fängt 
DCA-LAY-002
Domain must not depend on
Infrastructure

selects  classes in *.domain..
checks   no dependency on
         *.infrastructure..

Eine von 113 Regeln mit derselben Id in Java und .NET. Sie läuft im Build, also ist der Fehler ein roter Test und kein Review-Kommentar.

3 · die Grenze 
checkout.application.shared
  OrderRepository   ← Interface

checkout.adapter.outgoing
  .persistence
  JpaOrderRepository

Die Application sagt, was sie braucht; der Adapter setzt es um. Die Abhängigkeit zeigt jetzt nach innen, und dieselbe Regel beweist, dass das so bleibt.

Klein anfangen

Ein Bootstrap, ein Architekturtest

DCA einzuführen beginnt nicht mit einem Rewrite. Es beginnt mit einem Test, der rot wird, wenn eine Abhängigkeit in die falsche Richtung zeigt – in dem Projekt, das ihr schon habt.

# in Claude Code – dieselben Skill-Ordner funktionieren in Codex und OpenCode
/plugin marketplace add domain-centric-development/dca-marketplace
/plugin install dca-core@dca-marketplace

# in einem bestehenden Java- oder .NET-Projekt
/dca-bootstrap   # fügt die Building Blocks und einen Architekturtest hinzu,
                  # verdrahtet mit dem Layout, das dieses Projekt wirklich hat

./gradlew test-architecture   # Java
dotnet test                   # .NET – das Architekturprojekt, Debug-Build
  1. 01

    Anpassen, nicht überschreiben

    Marker-ähnliche Interfaces, die ein Projekt schon hat, werden per Alias übernommen oder behalten und in seiner Layout-Beschreibung deklariert. Nichts wird ersetzt, weil es anders heißt.

  2. 02

    Wählen, wofür ihr bereit seid

    Regeln kommen in Sets und werden je Projekt ausgewählt. Eine Regel, die noch nicht passt, wird per Id abgeschaltet, schriftlich – nicht stillschweigend ignoriert.

  3. 03

    Dann das Modell wachsen lassen

    Aggregates, Value Objects und Use Cases kommen als Nächstes, mit den Namenskonventionen und dem Glossar je Kontext, die die Regeln prüfen.

  4. 04

    Über die Pipeline liefern, wenn ihr wollt

    Eine Story durch Plan, Test, Build, Tidy, Judge und Document, mit einem Gate zwischen den Stufen, das die Testberichte des Projekts liest statt dem Wort einer Stufe zu glauben. Optional: die Architektur funktioniert auch ohne.

Was die Prüfungen zeigen und was nicht

Die Regel-Suiten prüfen Struktur: wo ein Typ liegen darf, wovon er abhängen darf, wie er heißen muss, welcher Layer welchen erreichen darf. 113 gemeinsame Ids in Java und .NET, dazu sechs nur für .NET, jede mit Selektor und Prüfung aufgeschrieben – ein grüner Lauf sagt also genau, welche kodierten Erwartungen gehalten haben, und die Kataloge sagen, welche das waren.

Sie sagen nicht, dass das Domänenmodell richtig ist, dass das Verhalten stimmt oder dass ein Use Case tut, was das Business gemeint hat. Dafür braucht es Verhaltenstests, einen Fachexperten und Review – und die Regeln markieren, was Urteil braucht, als informativ, statt es stillschweigend anzunehmen. Architekturtests prüfen Struktur; Verhaltenstests und fachliches Review prüfen, ob die Software das Richtige tut.

Warum es so gebaut ist

Architektur, an der man einen Agenten messen kann

Ein Modell, das schnell schreibt, braucht eine Grenze, mit der es nicht diskutieren kann. Das Ziel: Ein nichtdeterministischer Schreiber liefert überall dort ein deterministisches Ergebnis, wo eine Maschine es entscheiden kann – die Struktur des Codes und der Nachweis, dass ein Kriterium rot war, bevor es grün wurde. Wie verlässlich ein Agent die Domäne richtig trifft, ist noch nicht gemessen und wird hier nicht behauptet.

  1. 01

    Die Regeln sind ausführbar und haben Ids

    113 gemeinsame Ids wie DCA-USE-009, als Bibliothek für beide Stacks. Java erzwingt 108 und markiert 5 als informativ; .NET erzwingt 112 seiner 119 – sechs sind .NET-spezifisch –, markiert 4 als informativ und nennt die drei, die nicht anwendbar sind, mit Begründung. Eine gemeinsame Id heißt dieselbe Absicht; was sie selektiert und prüft, steht je Plattform aufgeschrieben statt als identisch angenommen.

    was die Regeln prüfen · Java und .NET im Vergleich

  2. 02

    Das Wissen ist maschinenlesbar

    Guide-Text, Marker-Verträge und jede Regel als ein verlinkter Graph im Open Knowledge Format. Der Agent baut aus dem Katalog statt aus einem halb erinnerten Blogpost – und nennt den Knoten, den er benutzt hat.

  3. 03

    Die Pipeline entscheidet, nicht die Stufe

    Eine Story läuft durch Plan, Test, Build, Tidy, Judge und Document; jede Stufe übergibt eine Datei statt eines Gesprächs. Dazwischen sitzt ein Gate, das ein Skript ist: ein End-User-Test je Akzeptanzkriterium, rot vor grün, gelesen aus dem Bericht des Test-Runners – ein Exit-Code sagt, wie ein Prozess endete, nicht, dass ein Test lief –, dann die Architektur-Suite und am Ende jede Aussage der Dokumentation gegen das Repository geprüft. Keine Stufe erklärt ihre eigene Arbeit für fertig; drei Runden ohne Annäherung halten an und fragen einen Menschen.

  4. 04

    Zwei Webshops, als Beleg und als Experimentierfeld

    Derselbe Shop in Java und .NET, hauptsächlich von Claude geschrieben, vom Autor gesteuert und reviewt, grün gegen die gemeinsamen Regel-Ids und dieselben sechs Flows. Sie sind auch da, um die Stellen zu finden, an denen zwei Agenten eine Story unterschiedlich bauen – jeder Unterschied ist eine Lücke, die in einer Regel, einem Marker oder dem Katalog zu schließen ist, nicht im Code.

Prinzipien

Streng, wo es sich auszahlt, pragmatisch, wo nicht

Konventionen, die sich prüfen lassen: Menschen und KI gehen von denselben Architekturerwartungen aus, und was sich kodieren lässt, ist kodiert. Der Rest wird als Ermessensfrage benannt, nicht angenommen.

  • Domäne ohne Framework Die Fachlogik hängt von nichts ab. Spring lebt in Adaptern und Infrastruktur.
  • Ports & Adapter Use Cases hinter typisierten Input Ports; Repositories, Stores und Publisher hinter Output Ports.
  • Architektur als Tests Strukturregeln sind ausführbare Tests – ArchUnit in Java, ArchUnitNET in .NET, dieselben Regel-Ids. Was Urteil braucht, ist als Review markiert, nicht stillschweigend angenommen. Erosion bricht den Build, nicht die Retrospektive.
  • Ubiquitous Language Namen kommen aus der Domäne, je Bounded Context. Die Regeln verweigern technische Suffixe an Domänentypen – Helper, Util, Impl – und Packages, die nach Patterns statt nach Begriffen heißen. Ein Fachwort, das zufällig technisch klingt, steht nicht auf der Liste.
  • Schrittweise Komplexität Vier Layer und eine einheitliche Tiefe im Application Layer: Use Cases liegen flach darunter oder gruppiert in fachlich benannten Features. DCA-USE-014 akzeptiert beides und verweigert die Mischung in einem Modul – die Wahl ist Sache des Projekts, die Konsistenz wird geprüft.
  • Pattern-Wahl je Subdomäne Kern-Subdomänen bekommen den ganzen taktischen Werkzeugkasten; unterstützende dürfen einfach bleiben.
