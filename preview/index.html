Domain-Centric Development

The domain at the center.
Everything else points inward.

Business rules end up in controllers, database entities and service classes — scattered, partly duplicated, with no single source of truth. Domain-Centric Architecture (DCA) places business rules in the domain; web, REST and persistence are adapters outside it. An architecture test fails the build when technology reaches into the domain — in Java and .NET.

What you get a framework update does not reach the domain, the build names the boundary that broke, and an agent is held to the same expectations as a colleague.

the mark is the architecture: one bounded context — adapters on the boundary, the domain at the core, a call coming in and its answers going out; neighbor contexts each with a core of their own

Infrastructure → Adapters → Application → Domain

One rule governs everything: dependencies point inward. The domain layer knows no framework, no database, no protocol — and an ArchUnit test suite fails the build when anyone forgets. It checks structure; whether the model is right stays a human question.

1 · the mistake 
package shop.checkout.domain;

import shop.checkout
  .infrastructure.persistence
  .OrderRow;

An entity reaches for the row it happens to be stored in. Nothing stops it, and a year later the model cannot be changed without the database.

2 · the rule that catches it 
DCA-LAY-002
Domain must not depend on
Infrastructure

selects  classes in *.domain..
checks   no dependency on
         *.infrastructure..

A structural rule shared by Java and .NET. It runs in the build, so the mistake is a red test rather than a review comment.

3 · the boundary 
checkout.application.shared
  OrderRepository   ← interface

checkout.adapter.outgoing
  .persistence
  JpaOrderRepository

The application states what it needs; the adapter implements it. The dependency now points inward, and the same rule proves it stays that way.

Start small

One bootstrap, one architecture test

Adopting DCA does not begin with a rewrite. It begins with one test that fails when a dependency points the wrong way — in an existing project.

# in Claude Code — the same skill folders work in Codex and OpenCode
/plugin marketplace add domain-centric-development/dca-marketplace
/plugin install dca-core@dca-marketplace

# on an existing Java or .NET project
/dca-bootstrap   # adds the building blocks and one architecture test,
                  # wired to the layout this project actually has

./gradlew test-architecture   # Java
dotnet test                   # .NET — the architecture project, Debug build
  1. 01

    Adapt, do not overwrite

    Marker-like interfaces a project already has are aliased or kept and declared through its layout description. Nothing is replaced because it has a different name.

  2. 02

    Select the rules for the project

    Rules come in sets and are selected per project. A rule that does not fit yet is switched off by id, in writing — not quietly ignored.

  3. 03

    Then grow the model

    Aggregates, value objects and use cases come next, with the naming conventions and the per-context glossary the rules check.

  4. 04

    Deliver through the optional pipeline

    One story through plan, test, build, tidy, judge and document, with a gate between the stages that reads the project's own test reports rather than a stage's word for it. Optional: the architecture works without it.

What the checks do and do not show

The rule suites check structure: where a type may live, what it may depend on, how it must be named and which layer may reach which. A green run means the selected checks passed; the rule catalogs document their scope.

A green run does not establish that the domain model is correct or that a use case does what the business meant. Those need behaviour tests, a domain expert and review. Rules that need judgement are marked as informational.

Why it is built this way

Architecture an agent can be held to

DCA is the architecture: a synthesis of Hexagonal Architecture, Clean Architecture and Domain-Driven Design, and the rule suite checks that the code keeps to it. Domain-Centric Development is how software is built with it, with AI support from dca-factory and the knowledge catalog. Domain-Centric Development aims for a deterministic result wherever a machine can check it: code structure and evidence that an acceptance test failed before it passed. How repeatably an agent gets the domain right is not measured yet.

  1. 01

    The rules are executable, and they have ids

    119 shared identifiers like DCA-USE-009, in a library for both stacks. Java enforces 113 and marks 6 informational; .NET enforces 119 of its 125 — six are .NET-specific — marks 5 informational and names the one that is not applicable, with the reason. A shared id means the same intent; what it selects and checks is written down per platform rather than assumed identical. The figures are the 0.5.0 catalog; the generated lists linked below are always current.

    see what the rules check · compare Java and .NET coverage

  2. 02

    The knowledge is machine-readable

    The catalog connects guide text, marker contracts and rules in a graph. Agents can look up the relevant node and cite it in their work.

  3. 03

    The pipeline decides, not the stage

    A story runs through plan, test, build, tidy, judge and document, with a file handed over at each stage. Gate scripts require an end-user test per acceptance criterion and read red-before-green evidence from the test runner’s report; an exit code alone does not show that a test ran. They also check the architecture suite and documentation claims against the repository. Three rounds without convergence require human review.

  4. 04

    Two webshops, as evidence and as the experiment field

    The same story was built once per stack, by an agent, on 10 September 2026. It surfaced two divergences between the two results — and both were closed in a rule and in the catalog, not in the shop code. That is what the pair is for: a difference between the implementations points at a gap in the shared artifacts.

Principles

Structural rules are checked; design choices need review

The rule suites encode structural conventions for developers and agents.

  • Framework-free domain Business logic depends on nothing. Spring lives in adapters and infrastructure.
  • Ports & adapters Use cases behind typed input ports; repositories, stores and publishers behind output ports.
  • Architecture as tests Structural rules are executable tests — ArchUnit in Java, ArchUnitNET in .NET, same rule ids. A structural violation fails the build.
  • Ubiquitous language Names come from the domain, per bounded context. The rules refuse technical suffixes on domain types — Helper, Util, Impl — and packages named after patterns instead of concepts. A domain word that happens to sound technical is not on that list.
  • Progressive complexity Four layers, and one consistent depth inside the application layer: use cases sit flat below it, or grouped into domain-named features. DCA-USE-014 accepts either and refuses a mix within one module — the choice is the project's, the consistency is checked.
  • Pattern choice per subdomain Core subdomains get the full tactical toolbox; supporting ones may stay simple.
