The domain at the center.
Everything else points inward.

Keep business logic independent of frameworks. Domain-Centric Architecture combines architectural guidance, executable checks and AI development tools for Java and .NET.

the mark is the architecture: one bounded context — adapters on the boundary, the domain at the core, a call coming in and its answers going out; neighbor contexts each with a core of their own

Infrastructure → Adapters → Application → Domain

One rule governs everything: dependencies point inward. The domain layer knows no framework, no database, no protocol — and an ArchUnit test suite fails the build when anyone forgets. It checks structure; whether the model is right stays a human question.

1 · the mistake 
package shop.checkout.domain;

import shop.checkout
  .infrastructure.persistence
  .OrderRow;

An entity reaches for the row it happens to be stored in. Nothing stops it, and a year later the model cannot be changed without the database.

2 · the rule that catches it 
DCA-LAY-002
Domain must not depend on
Infrastructure

selects  classes in *.domain..
checks   no dependency on
         *.infrastructure..

One of 113 rules with the same id in Java and .NET. It runs in the build, so the mistake is a red test rather than a review comment.

3 · the boundary 
checkout.application.shared
  OrderRepository   ← interface

checkout.adapter.outgoing
  .persistence
  JpaOrderRepository

The application states what it needs; the adapter implements it. The dependency now points inward, and the same rule proves it stays that way.

Start small

One bootstrap, one architecture test

Adopting DCA does not begin with a rewrite. It begins with one test that fails when a dependency points the wrong way — on the project you already have.

# in Claude Code — the same skill folders work in Codex and OpenCode
/plugin marketplace add domain-centric-development/dca-marketplace
/plugin install dca-core@dca-marketplace

# on an existing Java or .NET project
/dca-bootstrap   # adds the building blocks and one architecture test,
                  # wired to the layout this project actually has

./gradlew test-architecture   # Java
dotnet test                   # .NET — the architecture project, Debug build
  1. 01

    Adapt, do not overwrite

    Marker-like interfaces a project already has are aliased or kept and declared through its layout description. Nothing is replaced because it has a different name.

  2. 02

    Select what you are ready for

    Rules come in sets and are selected per project. A rule that does not fit yet is switched off by id, in writing — not quietly ignored.

  3. 03

    Then grow the model

    Aggregates, value objects and use cases come next, with the naming conventions and the per-context glossary the rules check.

  4. 04

    Deliver through the pipeline, if you want it

    One story through plan, test, build, tidy, judge and document, with a gate between the stages that reads the project's own test reports rather than a stage's word for it. Optional: the architecture works without it.

What the checks do and do not show

The rule suites check structure: where a type may live, what it may depend on, what it must be named, which layer may reach which. 113 shared identifiers in Java and .NET, plus six .NET-specific ones, each with its selector and its check written down — so a green run says exactly which encoded expectations held, and the catalogs say which those were.

It does not say the domain model is correct, that the behaviour is right, or that a use case does what the business meant. Those need behaviour tests, a domain expert and review — and the rules mark what needs judgement as informational rather than quietly assuming it. Architecture tests check structure; behaviour tests and domain review check whether the software does the right thing.

Why it is built this way

Architecture an agent can be held to

A model that writes fast needs a boundary it cannot argue with. The aim is to make a non-deterministic writer produce a deterministic result wherever a machine can decide it — the structure of the code, and the evidence that a criterion was red before it was green. How repeatably an agent gets the domain right is not measured yet, and is not claimed here.

  1. 01

    The rules are executable, and they have ids

    113 shared identifiers like DCA-USE-009, in a library for both stacks. Java enforces 108 and marks 5 informational; .NET enforces 112 of its 119 — six are .NET-specific — marks 4 informational and names the three that are not applicable, with the reason. A shared id means the same intent; what it selects and checks is written down per platform rather than assumed identical.

    see what the rules check · compare Java and .NET coverage

  2. 02

    The doctrine is machine-readable

    Guide text, marker contracts and every rule as one cross-linked graph in Open Knowledge Format. The agent builds from the catalog instead of from a half-remembered blog post — and cites the node it used.

  3. 03

    The pipeline decides, not the stage

    One story runs through plan, test, build, tidy, judge and document, each stage handing over a file rather than a conversation. Between them sits a gate that is a script: one end-user test per acceptance criterion, red before green read out of the runner's own report — an exit code says how a process ended, not that a test ran — then the architecture suite and, at the end, every documentation claim checked against the repository. No stage declares its own work done; three rounds without convergence stop and ask a human.

  4. 04

    Two webshops, as evidence and as the experiment field

    The same shop in Java and .NET, drafted mainly by Claude, directed and reviewed by the author, green against the shared rule ids and the same six flows. They also exist to find the places where two agents build one story differently — each difference is a gap to close in a rule, a marker or the catalog rather than in the code.

Principles

Opinionated where it pays, pragmatic where it doesn't

Conventions you can check: humans and AI start from the same architectural expectations, and the ones that can be encoded are encoded. The rest is named as a judgement call rather than assumed.

  • Framework-free domain Business logic depends on nothing. Spring lives in adapters and infrastructure.
  • Ports & adapters Use cases behind typed input ports; repositories, stores and publishers behind output ports.
  • Architecture as tests Structural rules are executable tests — ArchUnit in Java, ArchUnitNET in .NET, same rule ids. What needs judgement is marked as review, not quietly assumed. Erosion fails the build, not the retrospective.
  • Ubiquitous language Names come from the domain, per bounded context. The rules refuse technical suffixes on domain types — Helper, Util, Impl — and packages named after patterns instead of concepts. A domain word that happens to sound technical is not on that list.
  • Progressive complexity Four layers, and one consistent depth inside the application layer: use cases sit flat below it, or grouped into domain-named features. DCA-USE-014 accepts either and refuses a mix within one module — the choice is the project's, the consistency is checked.
  • Pattern choice per subdomain Core subdomains get the full tactical toolbox; supporting ones may stay simple.
